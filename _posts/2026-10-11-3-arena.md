On 10-02 we told the orchestrator to stop running our own league and use the team arena instead: tokenz-arena, built the evening before (first commit 10-01 20:35, 129 commits in all, [on GitHub](https://github.com/Battlecode-UnderTheC/tokenz-arena)). From then on, every verdict on every bot came from it. An import agent loaded 209 of our old local variants as drafts on the first day.

We built it because our teammates wanted to work on the bots too, and the local league from [the previous post]({% post_url 2026-10-11-2-mass-codegen %}) lived on one laptop. That league's simulator had also disagreed with the official judge, so the arena was built not to have one. Its design doc keeps two lessons from the league: a child against its parent is the cleanest signal, and local wins aren't server wins.

## The design

The first principle in tokenz-arena's [DESIGN.md](https://github.com/Battlecode-UnderTheC/tokenz-arena/blob/main/DESIGN.md) is "the official engine is the only judge". Every game is `unswbc run <map> A B --sandbox --seed S` at the toolkit version the competition server runs. There are no ports and no fast sims. The rest follows from wanting agents to use it without help:

- **One HTTP API.** Upload a bot as a zip, wait for its verdict, read its report, download replays and sources. An agent needs only `curl`. The same endpoints are exposed as MCP tools at `/mcp`, and `/llms.txt` explains the whole API on one page with live numbers. `docs/AGENTS.md` was the brief we handed to worker agents.
- **A submission is an experiment.** It names its parent and carries a note: the hypothesis and what changed. `/ideas` searches the notes paired with their verdicts, so an agent can check whether its idea already lost before writing it.
- **Drafts first.** A draft plays its parent and the current top 3 on the public maps, both seats, unranked, with a target of a verdict in about 5 minutes. `beats_parent` is simply more wins than losses against the parent. Promoting a draft gives it full placement against every active bot and a place on the leaderboard.
- **Bradley-Terry ratings** over ranked games among current submissions, a draw as half a win, on an Elo-like scale with a reference bot at 1000. Head-to-head tables sit next to the number.
- **No auth.** The arena is only reachable on the team's Tailscale network, and it asks Tailscale who is calling. Whatever runs on a teammate's laptop submits as that teammate.
- **No database.** State was one JSON file per submission and per game, written with an atomic rename. On 10-09 games moved into SQLite, because the server had become slow and used too much memory.

The map suites copied the league's scheme: official maps, tournament maps rebuilt from replays, a server suite with the maps and seeds seen in real server games, a weekly rotating set of generated maps, and a hidden holdout that only the top 4 played. From 10-05 the generated suites also drew on our own map generator (`tools/mapgen`), including "trick" maps built to punish one habit, such as rushing the centre.

The server bridge was the arena's window on the competition server. It downloaded every one of our server games once a minute and turned it into an arena game, with the opponent as an external bot `server:<team>`. It also held an auto-submit gate. A candidate had to be clearly #1 on the arena, beat the live bot head to head, be no worse on the holdout and server suites, and stay well inside the CPU limit; the gate uploaded at most once every 4 hours. On 10-02 a force-upload button was added that skips it. Both paths were used. The gate itself uploaded queen-guard-7, ring-plus-4, ring-plus-9, ring-sched-8, ring-sealed-2 and ring-shield-3; the rest went up through the button.

## Remote workers and the vast.ai scaler

The arena ran on a shared lab server. On 10-02 it gained remote workers (`docs/WORKERS.md`): any machine with Docker and a Tailscale key could lease games, run the official judge, and send back results with replays. A dead worker's games were played elsewhere.

The same evening the scaler (`arena/scaler.py`) started renting workers on vast.ai. Our notes record why vast.ai: about $2.5-4.5 per 1000 thread-hours, against $15-20 on AWS Spot. Every minute it rented enough cheap interruptible machines to clear the queue within about 5 minutes, and idle machines destroyed themselves. The caps we approved were $1 an hour, $10 a day and 6 machines, with a prepaid balance as the last guard. We didn't record what it actually spent. Its early bugs (outbidding itself, rehiring bad hosts, counting crashes as results) were fixed in the commit log within a morning. One fix was deployed to the live arena without approval, and from then arena changes needed explicit permission.

## The C++ judge

`unswbc run --sandbox` spends most of a game in Python glue around the wasm. On 10-02 and 10-03 we ported that glue to C++ (`judge/`, `docs/CPPJUDGE.md`), keeping everything that decides a game, the metered bot builds and the engine wasm, exactly as the official judge has them. The C++ judge produces the same replay byte for byte and used 1.6x to 7x less CPU. Whenever it couldn't be exact it handed the game to the official judge, and one game in 50 was played by both as a spot check, with the official result counting.

## Duels and ephemeral bots

From 10-04, workers could try a change before submitting it (`docs/DUELS.md`). An ephemeral bot is a zip checked like a submission but kept off the ladder, deleted after 24 hours. A duel plays any two bots on fresh random seeds (`random:N`), both seats, on any suite except the holdout. The fresh seeds keep a bot from being tuned to the ladder's fixed ones. The result reports W-D-L with a 95% interval and whether it excludes 50%. Duel games are stored apart, so nothing official can see them.

## The end

The last arena game was played on 10-09 at 05:57Z, when we stopped all workers. 10-09 was the submission day. By then it had played 291,668 games between 680 submissions, plus 629 duels with 30,656 games. Its replays came to about 196 GB zipped.

On 10-11 it became a static site, the [arena snapshot](https://battlecode-underthec.github.io/arena/) (repo [Battlecode-UnderTheC/arena](https://github.com/Battlecode-UnderTheC/arena)). We published it so that this series could point at the games it describes. The pages are the arena's own website, with the backend ported into a service worker that reads one SQLite file through HTTP range requests. The replays aren't stored. A game is deterministic given its map, seed and both bots, so the game page runs the official engine wasm (unswbc 1.2.9) and both bots' metered builds in a port of the judge's sandbox, one Web Worker per dragon, refilling 100M CPU points per turn. The toolkit's replay viewer shows the game as it runs and says whether the result matches the arena's record.
